# Security

PromoLite MCP is a portfolio project: a read-only MCP server over a **synthetic** retail dataset. This document says what
is protected, by which layer, and, just as important, what is **not**.

## Read this first: there is no authentication

The public endpoint (`/mcp`) has **no authentication**. Anyone who knows the URL can call every tool.

This is acceptable here **only because**:

1. the data is synthetic (generated by `scripts/generate-data.ts`, no real customer or business data), and
2. every tool is read-only (nothing can be created, changed or deleted), and
3. the worst a caller can do is read the same fake dataset or use up the rate limit.

A real deployment would put **OAuth 2.1 in front of `/mcp`** so each caller is identified and authorised. The MCP SDK
already ships the building blocks (`requireBearerAuth` and protected-resource metadata in `@modelcontextprotocol/express`),
so this is a known next step, not a redesign. It is not implemented (stretch goal).

## Layers (defense in depth)

If one layer fails, the others still hold. Outermost first:

| # | Layer | Where | What it stops |
|---|---|---|---|
| 1 | TLS | the platform or Caddy in front (see `docs/DEPLOY.md`) | eavesdropping and tampering on the wire |
| 2 | Nginx request limits | `docker/nginx.conf` | 10 requests/second per IP (burst 20, then `429`); bodies over 64 KB (`413`); slow-loris (10 s header/body timeouts); every path except `/mcp` and `/health` is `404` |
| 3 | Nginx header hygiene | `docker/nginx.conf` | no version banner; `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Cache-Control: no-store`, HSTS, and `default-src 'none'` for the JSON responses |
| 4 | Host-header validation | `src/server/httpApp.ts` | DNS rebinding: a hostile web page cannot reach the server through a name we did not list (`ALLOWED_HOSTS`) |
| 5 | Origin + CORS allowlist | `src/server/httpApp.ts` | a browser page may call `/mcp` only from an exactly-listed origin (scheme + host + port); anything else gets `403`. Non-browser clients (Claude's servers, curl) send no `Origin` and are unaffected |
| 6 | App rate limit | `src/server/httpApp.ts` | 300 requests/minute per client IP, a second layer for deployments that have no Nginx (platform proxy only) |
| 7 | Body size limit | `src/server/httpApp.ts` | `64kb` JSON limit, `413` with a small JSON error |
| 8 | Input validation | `src/server/schemas.ts` | every tool argument is checked by a Zod schema (ISO dates, integer ranges, enums) before any code runs |
| 9 | Container hardening | `docker/Dockerfile`, `docker-compose.yml` | runs as the non-root `node` user, read-only filesystem, all Linux capabilities dropped, `no-new-privileges`, app not published to the host (only Nginx is) |
| 10 | Iframe sandbox + strict CSP | the **host** + `src/server/ui.ts` | what a view (untrusted HTML shown inside a chat app) can do, see below |

## What the sandbox and the CSP protect

A view is a web page that a chat app shows inside a **sandboxed iframe**. The host (Claude, VS Code, ...) enforces the
sandbox: the view cannot read the host page, its cookies or its storage, and talks to the host only through `postMessage`.

On top of that, every view declares a **strict Content Security Policy** in its resource metadata (`_meta.ui.csp`):

```json
{ "connectDomains": [], "resourceDomains": [], "frameDomains": [], "baseUriDomains": [] }
```

**The CSP allows nothing**: no outside network requests (`connect-src`), no outside scripts, styles, fonts, images or
media, no nested iframes, no `<base>` changes. This works because each view is a single self-contained HTML file with its
JavaScript and CSS inlined and no CDN fonts. The view receives its data from the host, not from the network.

This was tested, not just configured: in a reference MCP Apps host, a view that tried to load a Google Font stylesheet and
`fetch("https://example.com")` had **both blocked by the browser** (`style-src` and `connect-src` violations), and the view
kept working. `tests/tools.test.ts` locks the policy in: it fails if any view's CSP is not empty or if a view contains a
tag that would load an outside resource.

The CSP is enforced by the **host**. A host that ignores `_meta.ui.csp` would not enforce it; that is outside this
server's control.

## Input handling

- All inputs go through Zod. Unknown product IDs, unknown stores, bad dates and out-of-range numbers return a clear
  `isError` result and never reach the data layer.
- **No input ever reaches a file path or a shell command.** The server has exactly two file reads: the four CSV files
  (names fixed in code) and the built view files (names fixed in code). There is no `exec`, `spawn`, `eval` or dynamic
  `import`.
- Errors that are not the caller's fault are logged on the server and answered with a generic `Internal server error`:
  no stack traces or paths in responses.

## Supply chain

`npm ci` installs exactly the versions in `package-lock.json` (CI and the Docker build both use it). The runtime image
installs production dependencies only. There is no automated dependency scanning yet (Dependabot or `npm audit` in CI would
be the next step).

## Out of scope (not handled here)

- **Authentication and per-user authorisation** (see the top of this file).
- **DDoS protection.** The rate limits stop a runaway client, not a distributed attack. A real deployment would sit behind a
  CDN or the platform's protection.
- **Prompt injection through data.** Tool results are model-facing text. Here the text comes from a synthetic dataset we
  control. With real data, free-text fields (names, notes) could carry hostile instructions and would need handling.
- **Secrets management.** There are no secrets: no API keys, no database, no accounts.
- **Monitoring, alerting and audit logging.**
- **Data privacy.** None needed: the data is synthetic and says so in the README.
